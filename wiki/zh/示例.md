# 示例

仓库里每个示例都能直接编译运行（`cargo run --example <名字>`），是上手最快的方式。

| 示例 | 演示内容 | 运行 |
|---|---|---|
| `hello` | 单文件跑通 h2c 客户端 + 服务器 | `cargo run --example hello` |
| `greeter` | gRPC 服务器 + 客户端：unary（原始字节 + 类型化）、错误状态 | `cargo run --example greeter` |
| `streaming` | 服务器流式返回 `Body::Channel`，客户端逐块消费 | `cargo run --example streaming` |
| `priority` | RFC 9218：高优先级流优先于低优先级积压调度 | `cargo run --example priority` |
| `redirects` | 自动跟随 302 跳转链（RFC 9110） | `cargo run --example redirects` |
| `fingerprint` | 打印 JA3 / JA4 / Chrome HTTP/2 指纹值 | `cargo run --example fingerprint` |
| `https` | HTTPS（TLS 1.2 + 1.3）端到端：自签名 Ed25519 身份、校验客户端、ALPN 上的 h2 + HTTP/1.1 | `cargo run --example https` |
| `h3` | HTTP/3（QUIC v1 + TLS 1.3）端到端：冷连接、池化复用、流控、并发流、证书拒绝 | `cargo run --example h3` |
| `ws_echo` | 同一进程内 WebSocket 回声服务器 **与** 客户端：升级、文本/二进制往返、同连接服务端主动推送、子协议、干净关闭 | `cargo run --example ws_echo` |
| `ws_client` | 带生产级配置的 WebSocket 客户端：子协议、Origin、压缩偏好、读超时、有界关闭 | `cargo run --example ws_client` |
| `grpc_streaming` | gRPC 服务端流/客户端流/双向流、deadline、gzip 协商、metadata + 拦截器 | `cargo run --example grpc_streaming` |
| `grpc_health` | `grpc.health.v1.Health` 的 `Check` 与 `Watch`，protobuf 手工编码 | `cargo run --example grpc_health` |
| `grpc_framing` | 单独演示 gRPC 的 5 字节长度前缀消息帧 | `cargo run --example grpc_framing` |
| `grpc_compression` | `grpc-encoding: gzip` 背后的从零实现 gzip / DEFLATE / CRC-32 | `cargo run --example grpc_compression` |
| `protocol_core` | HPACK + h2 编解码在内存管道上运行（无 socket）+ 自带哈希 | `cargo run --example protocol_core` |
| `huffman` | HPACK Huffman（RFC 7541 §5.2）与表驱动解码器 | `cargo run --example huffman` |
| `h1_codec` | HTTP/1.1 线上编解码原语，不用任何 socket | `cargo run --example h1_codec` |
| `h3_frames` | 单独的 HTTP/3 帧层（RFC 9114 §7.2） | `cargo run --example h3_frames` |
| `qpack` | QPACK 编解码（RFC 9204）：静态表、前缀整数、Huffman、阻塞流 | `cargo run --example qpack` |
| `quic_varint` | QUIC 可变长整数（RFC 9000 §16） | `cargo run --example quic_varint` |
| `quic_protection` | QUIC v1 包保护（RFC 9001 §5）：Initial 密钥、AEAD 封包、头保护 | `cargo run --example quic_protection` |
| `pool` | 单独演示工作窃取线程池 | `cargo run --example pool` |
| `bytes` | 零拷贝 `Bytes` 窗口与 `BytesMut` 追加缓冲 | `cargo run --example bytes` |
| `crypto` | 指纹背后的自带 MD5 / SHA-256 | `cargo run --example crypto` |
| `diag` | loopback h2 echo 诊断 | `cargo run --example diag` |

## hello

单文件：随机端口起服务器，然后用 HTTP/2 客户端 GET/POST。一切入门的起点。

## greeter

后台 gRPC 服务器带两个方法 + 客户端调用——原始字节 `call`、类型化 `call_unary`、以及客户端侧暴露 `grpc-status` 的错误路径。

## streaming

服务器返回 `Body::Channel`，生产者线程喂数据，客户端从 channel 接收端逐块消费。HTTP/1.1（chunked）与 HTTP/2 下都可用。

## priority

先发 32 个 `urgency=7` 请求，再发一个 `urgency=0` 请求。WUCS 调度器不能让低优先级积压饿死高优先级流——示例打印高优先级请求的完成耗时。

## redirects

`302 -> 302 -> 200` 两跳链，客户端透明跟随，最终响应直接返回。

## fingerprint

打印确切的 ClientHello 参数（`chrome_tls_profile`）、JA3 字符串/哈希、JA4 与 Chrome HTTP/2 SETTINGS 顺序——这些是喂给你自己的 TLS 层的值。

## https

用 `tests/certs/` 里的自签名 Ed25519 证书（DER）开一个 HTTPS 服务器，客户端以同一张证书为根做校验。TLS 之上同时服务 h2（ALPN）与 HTTP/1.1；客户端 GET/POST `https://` URL 并打印状态码与响应体。真实部署换成你自己的证书链 + 私钥。

## protocol_core

无 socket 的 `no_std` 核心：HPACK 编解码往返、在内存管道上驱动的 h2 `Connection`（任何实现 `io::Read`/`io::Write` 的类型都行）、零依赖 MD5/SHA-256。

## diag

loopback h2 echo，打印状态码与响应体——接真实端点前快速确认栈正常。

## h3

一个 QUIC 服务端 + 池化的 H3 客户端，用与 `https` 相同的自签名身份：第一个请求支付 QUIC 握手 + TLS 1.3 + Retry 地址验证的代价，之后的请求都在同一条连接上开新流（~1 RTT），随后演示大响应流控、并发多路复用与证书拒绝。

## ws_echo

一个文件里的完整 WebSocket 往返：服务端钩子接受 `/echo`，客户端升级、收发一条文本与一条二进制消息、请求服务端在同一条连接上主动推送（跨线程 `WsSender` 路径）、打印协商出的子协议与 `permessage-deflate` 参数，最后干净关闭——客户端与服务端的 `on_close` 都会跑到。

## ws_client

单独使用客户端那一半，可以连任意端点（`ws://` 或 `wss://`，包括公共 echo 服务）：子协议 offer、`Origin` 头、压缩偏好、读超时与有界的关闭握手——生产里真正重要的那些选项，并把对端同意了什么打印出来。

## grpc_streaming

`greeter` 没覆盖的调用形状：服务端流、客户端流、双向流，加上会以 `DEADLINE_EXCEEDED` 浮出水面的 `grpc-timeout`、通过 `grpc-encoding` 协商的 gzip、请求 metadata 与拦截器。

## grpc_health

不依赖 protobuf 代码生成地提供 `grpc.health.v1.Health`：两条极小的 protobuf 消息手工编码，`Check`（unary）与 `Watch`（服务端流）都跑在本 crate 自己的 HTTP/2 + gRPC 分帧上。

## grpc_framing

每条 gRPC 消息戴的那个 5 字节前缀——1 字节标志（`0` identity、`1` gzip）加大端长度——在隔离环境下组帧与再解析，包括超限拒绝。

## grpc_compression

`grpc-encoding: gzip` 背后的从零实现 RFC 1951/1952 编解码器：在高可压缩载荷上跑，并处理一个解压炸弹（膨胀后的大小必须被拒绝，而不是先分配）。

## huffman

RFC 7541 §5.2 的编码表配两级别表驱动解码器：编码、解码，以及让恶意 Huffman 块（padding、EOS、截断）直接失败而不是空转的检查。

## h1_codec

不涉及 socket 的请求行/状态行与头解析原语，包含消息边界的严格性（尾随垃圾被拒）——它保证本服务端与代理对「请求在哪里结束」不会产生分歧。

## h3_frames

单独的 HTTP/3 帧层（RFC 9114 §7.2）：varint 寻址的 `type` + `length` + payload，未知扩展帧原样保留而不是拒绝。

## qpack

隔离的 QPACK 编解码（RFC 9204）：99 项静态表、前缀整数、Huffman 字面量，以及 HTTP/3 对端依赖的阻塞流计数。

## quic_varint

QUIC 的自描述整数（RFC 9000 §16）：最高两位选择 1 / 2 / 4 / 8 字节编码，于是小值在线上只占一个字节。

## quic_protection

QUIC v1 包保护（RFC 9001 §5）：Initial 密钥由连接 ID 推导（HKDF → AES-128-GCM）、载荷以包号为 nonce、头部为 AAD 做 AEAD 封装，头部保护再掩上长度字段。

## pool

每条服务端/客户端连接之下的工作窃取调度器：每 worker 私有 LIFO 栈、全局 FIFO 窃取队列、任务内嵌提交，以及「优先挑空闲最久 worker」。

## bytes

零拷贝 `Bytes` 窗口：`slice`、`split_to`、`split_off`、`freeze` 只在同一块分配上移动 (start, len) 窗口而不复制字节——这正是编解码路径能做到零分配的原因。

## crypto

零依赖的 MD5（RFC 1321）与 SHA-256（FIPS 180-4），同时也是 JA3/JA4 的底座——并按公开测试向量逐条校验打印。
