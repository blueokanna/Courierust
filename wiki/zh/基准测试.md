# 基准测试

仓库自带**零依赖**基准测试（`benches/throughput.rs`）——不用 criterion，与 crate “不引入第三方库” 的规矩一致。它测的是本 crate 真正声称的能力：keep-alive 往返、多核扩展、HTTP/2 多路复用、RFC 9218 优先级行为。

## 怎么跑

```bash
cargo bench --bench throughput
```

用 `bench` profile（`lto = "thin"`、`codegen-units = 1`）构建并逐项打印：

```
h1_sequential:            22882 req/s (total=0.874s, n=20000, workers=1)
h1_concurrent:            71902 req/s (total=0.223s, n=16000, workers=8)
h2_multiplex:             35892 req/s (total=0.178s, n=6400, workers=32)
h2_priority_high_latency: 1.18 ms (high-urgency completion, workers=64)
```

GitHub Actions 的 `benchmark.yml` 在 push 到 `main`（`src/`、`benches/`、`Cargo.toml` 变更时）和手动触发时运行同一条命令，并把数字写进 run summary。

## 每项在测什么

| 用例 | 场景 | 说明 |
|---|---|---|
| `h1_sequential` | 20,000 次 GET，单客户端、单 keep-alive 连接 | HTTP/1.1 编解码的原始往返延迟 |
| `h1_concurrent` | 8 线程 × 2,000 次 GET，每线程一个客户端 | 多核扩展；按 worker 分片的连接池避免锁竞争 |
| `h2_multiplex` | 32 线程 × 200 次 GET，共享（≤4 条）h2 连接 | 交错流下的 HTTP/2 多路复用吞吐 |
| `h2_priority_high_latency` | 先挂起 64 个低优先级请求，再发一个 urgency=0 的请求 | WUCS 防饥饿：高优先级流多快完成 |

## 怎么读数字

- `h1_concurrent` 应随核数扩展；如果不扩展，瓶颈通常在客户端/服务器的锁，而不是线上编解码。
- `h2_multiplex` 在 loopback 下比 `h1_concurrent` **低**是正常的：每个流有分帧开销，调度器在流之间轮转。关键看它能否在高负载下保持稳定不塌。
- `h2_priority_high_latency` 是单个 urgency=0 请求在一堆低优先级工作之后完成的延迟。亚毫秒到低毫秒是健康的；如果爬到几十毫秒，说明调度器饿死了高优先级桶（违反 RFC 9218 §10）。

## 说明

- 数字只反映 loopback，且取决于运行机的核数、OS 与时钟——当作**相对**测量，别当绝对指标。
- 任何请求错误都会让 harness panic，所以红色运行 = 真实协议 bug，而不是机器慢。
- Windows 上 `cargo bench` 把结果打到 stderr，CI 里用 `2>&1` 捕获。
