# 基准测试

`benches/` 子 crate（`courierust_benchmark`）提供两套基准：

- `throughput` — 零依赖自测：keep-alive 往返、多核扩展、HTTP/2 多路复用、RFC 9218 优先级行为。
- `compare` — 与主流栈（**hyper** / **reqwest** / **tiny_http**）的跨库对比，带进程级计数分配器，分配数也可比。

## 怎么跑

```bash
cargo bench --manifest-path benches/Cargo.toml --bench throughput
cargo bench --manifest-path benches/Cargo.toml --bench compare
```

用 `bench` profile（`lto = "thin"`、`codegen-units = 1`）构建。GitHub Actions 的 `benchmark.yml` 在 push 到 `main` 与手动触发时运行两套并把数字写进 run summary。

## 自测（`throughput`）

```
h1_sequential:            22882 req/s (total=0.874s, n=20000, workers=1)
h1_concurrent:            71902 req/s (total=0.223s, n=16000, workers=8)
h2_multiplex:             35892 req/s (total=0.178s, n=6400, workers=32)
h2_priority_high_latency: 1.18 ms (high-urgency completion, workers=64)
```

| 用例 | 场景 | 说明 |
|---|---|---|
| `h1_sequential` | 20,000 次 GET，单客户端、单 keep-alive 连接 | HTTP/1.1 编解码的原始往返延迟 |
| `h1_concurrent` | 8 线程 × 2,000 次 GET，每线程一个客户端 | 多核扩展；按 worker 分片的连接池避免锁竞争 |
| `h2_multiplex` | 32 线程 × 200 次 GET，共享（≤4 条）h2 连接 | 交错流下的 HTTP/2 多路复用吞吐 |
| `h2_priority_high_latency` | 先挂起 64 个低优先级请求，再发一个 urgency=0 的请求 | WUCS 防饥饿：高优先级流多快完成 |

## 跨库对比（`compare`）

loopback 顺序 keep-alive 往返，每项 2,000 请求、单客户端。`raw_tcp_floor` 是**不带任何 HTTP** 的裸 socket 写+读——它是该平台的系统调用地板，也是任何 HTTP 栈在这台机器上的上限。样例（Windows，2026-08；当时机器负载较高，绝对数偏低——**看比值**）：

```
raw_tcp_floor:                                    ~12,000 req/s   (平台地板)
h1 courierust client + courierust server:         9,190 req/s   47 allocs/req
h1 courierust client + tiny_http server:          6,854 req/s   64 allocs/req
h1 courierust client + hyper server:              8,952 req/s   32 allocs/req
h1 reqwest client + courierust server:            3,953 req/s   73 allocs/req
h1 reqwest client + tiny_http server:             4,488 req/s   88 allocs/req
h2 courierust client (h2c):                       5,263 req/s   73 allocs/req
h2 courierust client + hyper server (h2c):        3,747 req/s   59 allocs/req
h2 reqwest client (h2c):                          2,886 req/s  100 allocs/req
```

结论：

- **courierust 贴住系统调用地板**。h1 全栈达到裸 TCP 地板的 ~76%；主流组合（reqwest+tiny_http）只有 ~37%。HTTP 栈与 `raw_tcp_floor` 的差距就是线上编解码还剩的提升空间——courierust 在这台平台上已几乎无余量。
- **服务器侧**：courierust、hyper、tiny_http 三者差距在 35% 以内（都受地板约束）；真正的分水岭在客户端与分配数。
- **客户端侧**：同一服务器下 courierust 的 h1 客户端比 reqwest 快 ~2.3×；h2c 客户端比 reqwest 快 ~1.8×。
- **分配**：courierust 全栈 47 次/请求 vs reqwest+tiny_http 88 次。连接级缓冲回收（`Scratch`）与 h2 帧缓冲复用是压低它的原因。

## 怎么读数字

- `h1_concurrent` 应随核数扩展；如果不扩展，瓶颈通常在客户端/服务器的锁，而不是线上编解码。
- `h2_multiplex` 在 loopback 下比 `h1_concurrent` **低**是正常的：每个流有分帧开销，调度器在流之间轮转。关键看它能否在高负载下保持稳定不塌。
- `h2_priority_high_latency` 是单个 urgency=0 请求在一堆低优先级工作之后完成的延迟。亚毫秒到低毫秒是健康的；如果爬到几十毫秒，说明调度器饿死了高优先级桶（违反 RFC 9218 §10）。

## 说明

- 数字只反映 loopback，且取决于运行机的核数、OS 与时钟——当作**相对**测量，别当绝对指标。
- 任何请求错误都会让 harness panic，所以红色运行 = 真实协议 bug，而不是机器慢。
- Windows 上 `cargo bench` 把结果打到 stderr，CI 里用 `2>&1` 捕获。
- `compare` 用进程级计数分配器，`allocs/req` 统计整个进程（含 harness 本身）的分配——各库之间可比。
