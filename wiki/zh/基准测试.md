# 基准测试

`benches/` 工作区提供以 release profile 运行的可执行套件：

- `throughput`：Courierust 的 HTTP/1.1 keep-alive、并行 HTTP/1.1、h2c 多路复用，以及 HTTPS + HTTP/2。
- `compare`：与 hyper、reqwest 的配对 loopback 对比。
- `concurrency`：针对服务端调度器的不完整请求头与慢发送连接压力测试。
- `network`：明确的跨机 client/server 端点；不会把 loopback 标成跨机证据。
- `interop`：针对 hyper、hyper-util、reqwest 的协议兼容性验证；它不是性能基准。

运行与 GitHub Actions 相同的套件：

```bash
cargo bench --manifest-path benches/Cargo.toml --locked --bench throughput
cargo bench --manifest-path benches/Cargo.toml --locked --bench compare
cargo bench --manifest-path benches/Cargo.toml --locked --bench concurrency
cargo bench --manifest-path benches/Cargo.toml --locked --bench interop
```

基准 profile 使用 thin LTO 和单个代码生成单元。任一协议错误或断言失败都会使对应 suite 以非零状态退出。GitHub Actions 为每个 suite 分别保存日志，在运行摘要中发布结构化报告，并上传报告和原始日志。

## 吞吐基准

`throughput` 测量 loopback 上完整的请求/响应往返。每个请求都会校验状态并完整消费响应体后才计入结果。适用场景覆盖空响应、1 KiB 和 64 KiB 响应。

| 用例族 | 传输 | 负载 |
| --- | --- | --- |
| `h1_sequential` | HTTP/1.1 | 单个 keep-alive 客户端连接 |
| `h1_parallel_w*` | HTTP/1.1 | 1、4、8 个 worker 的独立客户端 |
| `h2_multiplex_w*` | h2c prior knowledge | 一个池化 HTTP/2 连接，1、8、32 个 worker |
| `https_h2_sequential` | TLS 1.2/1.3 + HTTP/2 | 证书验证、ALPN 与加密请求/响应路径 |

每条结果记录 RPS、响应吞吐量、P50/P75/P90/P95/P99 请求延迟和实际服务端线程数。可使用 `BENCH_REQUESTS` 和 `BENCH_SERVER_THREADS` 覆盖默认请求数与服务端 worker 数。HTTP/1.1 并行用例会把实际服务端线程数提升到至少客户端 worker 数，因为 Linux 的阻塞式服务端模型会为每条空闲 keep-alive 连接占用一个 worker。

## HTTP/3（`h3` bench）

`h3` bench（`cargo bench --manifest-path benches/Cargo.toml --bench h3`）测量池化 HTTP/3 路径：冷连接、热路径顺序请求、64 KiB 上传、64 KiB 响应下载，以及单条 QUIC 连接上的并行 worker。`BENCH_REQUESTS`、`H3_WORKERS`、`BENCH_BODY_BYTES`、`BENCH_RESPONSE_BYTES` 调节负载；`H3_SCENARIOS=1` 跑完整的 body 大小 × 方向 × worker 矩阵，`H3_SWEEP=1` 在子进程中扫 worker × ACK-delay × cwnd。

reactor 的延迟模型是 deadline 驱动而不是节拍驱动。poll timeout 是 `max(0, 下一个协议 deadline − 当前时刻)`——最早的待发 ACK 批次、loss/PTO 定时器、路径校验或请求超时——并且每个 burst 的第一个 ack-eliciting 包立即回 ACK（后续包合并进这同一个 ACK）。固定 poll tick 曾经门控每个 cwnd-limited round：每个 ACK 都要等满 `ack_delay()` 再加下一次 poll 唤醒，环回上给延迟尾部加了一个多毫秒台阶。改成即时 ACK + deadline 折叠后，`h3_sequential` 是 p50 ~115 µs / max ~0.2 ms，`h3_parallel`×4 是 p50 ~180 µs / p99 ~0.35 ms，64 KiB 上传 p50 ~1.15 ms。`courierust_net::Stats` 的 `h3_ack_deferred` / `h3_credit_stalls` 可以区分一条流是被 ACK 批次窗口限速还是被拥塞窗口限速。

`COURIERUST_H3_ACK_DELAY_MS`、`COURIERUST_H3_MIN_ACK_DELAY_MS`、`COURIERUST_H3_CWND`、`COURIERUST_H3_SERVER_POLL_MS`、`COURIERUST_H3_CLIENT_*_POLL_MS` 分别覆盖对应旋钮。`COURIERUST_H3_TRACE` 开启逐包事件流（负载下很慢——测 timing 时别开），`COURIERUST_H3_TRACE_MS` 只开启每请求阶段分解（`total_us|send_us|wait_headers_us|recv_body_us`），把慢路径归因到具体阶段而不带逐包开销。

环回 H3 数字是单 runner 证据：取决于 CPU 配额、内核调度和后台负载。跨主机测量请用 `network` bench，未提供 `COURIERUST_NETWORK_URL` 时报告为 `not_configured`，绝不虚构。

## WebSocket（`ws` bench）

`ws` 基准（`cargo bench --manifest-path benches/Cargo.toml --bench ws`）分三层测量 WebSocket 路径，并把前两层与 `tungstenite 0.30`、`tokio-tungstenite 0.30` 在**同一进程、同一编译配置、同一次运行**里对比（跨运行比较受机器负载影响会失真 3–10 倍，文档里明说了这一点）：

- **codec**：多种载荷大小下的编码、掩码、解码与 UTF-8 校验；
- **回声往返**：客户端掩码请求 → 服务端未掩码响应，本 crate 两端与参考实现跑在同一对 socket 上；
- **单向推送**：服务端向只读客户端推一串消息（扇出形状），有界发送队列与 reactor 唤醒路径在这里体现。

被测量的引擎决策（16 字节车道掩码、超过 8 KiB 的零拷贝读取、可复用的 DEFLATE 上下文、小帧一次 write）与数字写在一起，**输掉的行也写在一起**——本 crate 两端之间传 256 KiB 消息比 tungstenite 的组合慢，已定位的原因（以及背后的 Windows socket 超时发现）在 `benches/WS_BENCHMARK.md`。`WS_BENCH_SECTION=echo|push|codec` 可以只跑其中一层。

## 复杂度（时间与空间）

`cargo bench --manifest-path benches/Cargo.toml --bench complexity` 测的是代价*如何增长*，而不只是“快不快”。每个家族取跨三个数量级的多个规模，每个测量点取三次重复的最小值（噪声只会让测量变慢，取最小值才是正确估计），并拟合两个模型：仿射模型 `cost = a + b·n`（固定开销 + 每单位开销，附 R²），以及相邻规模对的指数——其中位数命名报告的复杂度量级，同时打印最差的一对，避免单个噪声点被当成趋势。空间分两层归因：每操作由编译进基准二进制的计数分配器归因，每连接用 1 与 65 条空闲 keep-alive 连接之间的 live-bytes/RSS 差值归因。

| 家族 | 随什么变化 | 对比对象 |
|---|---|---|
| `codec` | WebSocket 组帧/掩码/解码/UTF-8，64 B → 1 MiB | `tungstenite` |
| `http` | 一次 GET 往返，1 KiB → 1 MiB | `reqwest`（hyper） |
| `headers` | 请求头数量，4 → 64 | `reqwest`（hyper） |
| `connections` | 一条空闲 keep-alive 连接的内存 | 阻塞驱动、hyper + tokio |
| `deflate` | permessage-deflate 编码（复用 vs 全新建上下文）与解压 | 工作区里没有公平的第三方对端 |

方法论、一次实测、每连接内存以及每条热路径的算法量级都在 `benches/COMPLEXITY.md`；当前数字由 CI 报告给出。

## 跨库对比

`compare` 在测量一侧时固定另一侧的 peer：

- 客户端对比：Courierust 与 reqwest 客户端连接同一个 hyper 服务端。
- 服务端对比：同一个 reqwest 客户端分别连接 Courierust 和 hyper 服务端。
- 协议：HTTP/1.1 与 h2c prior knowledge。
- 负载：1 KiB、64 KiB 的顺序响应，以及 8 worker 的 1 KiB 客户端并发负载。
- 每次测量均会完整消费并校验响应体。

每个配置均运行偶数轮，并在每轮交替执行顺序，确保任一实现不会总是先测量。输出结果合并所有轮次，并包含实际重复次数。可用 `BENCH_REPETITIONS`、`BENCH_REQUESTS`、`BENCH_PARALLEL_REQUESTS` 和 `BENCH_COMPARE_WORKERS` 调整负载。若设置奇数轮，程序会向上取整为偶数轮，以保证执行顺序平衡。

`raw_tcp_floor` 仅是四字节 echo 的传输层参考值，不是 HTTP 对比行，也不能据此宣称 HTTP 性能比例。基准不再发布进程级分配次数，因为服务端线程、运行时、日志和 harness 自身的分配无法归因到某一个客户端或服务端实现。

大 body 的 h2c 对照现在使用 async Reqwest 和共享 Tokio runtime，并完整消费请求体与响应体。旧的 blocking Reqwest 测量在两个对端都出现约 41 ms 固定等待；该 harness 异常只保留在历史报告中，不是性能证据。h2c 客户端结果只适用于对应负载：单 worker 不代表全面领先，8 worker 必须结合连接策略和延迟尾部解读。

`network` 需要由两台独立机器运行：服务端设置 `COURIERUST_NETWORK_ROLE=server` 与 `COURIERUST_NETWORK_BIND=0.0.0.0:8080`，客户端将 `COURIERUST_NETWORK_URL` 指向远端。HTTPS 使用 `COURIERUST_NETWORK_TLS=true` 以及 DER 证书/私钥路径。没有远端 URL 时报告会标为 `not_configured`，不会虚构跨机数字。

`concurrency` 记录不完整 HTTP/1.1 请求头与慢发送连接，并输出平台和 Windows event-driven 是否启用；Linux 阻塞池结果不会被表述成 Windows 事件循环证据。

## 解读结果

结果以 `RESULT|...` 记录输出，便于机器解析，包含协议、负载、客户端 worker 数、服务端线程数、请求数、RPS、响应 MB/s、分位延迟和样本数。只比较协议、负载、worker 数、服务端线程数及测量层相同的行。loopback 数据会受到 runner CPU 配额、内核调度和后台负载影响，应只用于同一 runner 上的受控对比，不能作为通用性能结论。

`interop` 输出 `INTEROP|...` 记录。任何失败或超时都是兼容性回归，会使 CI 失败，与性能数值无关。

Workflow 还会运行 `h2_frame` 与 `hpack_block` 两个 `cargo-fuzz` target。生成的 `Github_Action_Benchmark.md` 会在 main 分支 push 后提交到仓库本身，可直接在 GitHub 仓库中查看，而不只存在于 Actions 摘要或 artifact 中。
