# courierust_hpack

HPACK（RFC 7541）头块编码器与解码器。`no_std`、零依赖。

## 必须对的那一半

**解码器。** HPACK 是那种"差不多对 = 完全错"的格式——头块解错一位，整条连接就失步了。所以解码器是**逐字节对照 RFC 7541 附录 C 官方向量（C.2–C.6）**验证的，Huffman 解码器对着完整规范表测。

编码器就好办多了（RFC 给编码器留了自由度），但我还是按规范策略来：

1. 全匹配 → indexed；
2. 否则 literal-with-indexed-name，可复用的进动态表；
3. 敏感字段（`authorization`、`cookie`……）→ 永远 never-indexed；
4. 能让线上形式变短就用 Huffman。

## 里面有什么

- **61 项静态表 + 动态表**，哈希加速的索引查找。
- **8-bit 两级查表 Huffman 解码**——解码表构建期生成，短码走快速路径。不逐位爬。
- `HeaderField` 带 `never_indexed` 标记，"永远别进动态表"这个意图能完整走完往返。
- 编码器和解码器共用同一套表机制——没有两套实现会漂移。

## 你没要求的加固

HPACK 不设防就是个压缩炸弹投递系统。解码器拒绝：

- 前缀整数溢出；
- Huffman EOS 码与非法 padding；
- 超过对端 SETTINGS 上限的动态表大小；
- 超过配置上限的头列表。

想用 3 字节让我分配 4GB 的对端，会拿到一个错误，而不是一块内存。

## 为什么不直接用 `hpack` crate

因为这个栈是 `no_std` 零依赖，而且——跟这里所有东西一样——这是真正*懂*这个格式的方式，而不是赌某个依赖把它写对了。
